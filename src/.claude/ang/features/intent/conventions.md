# Delivery intent conventions

`project-context/10k/intent.md` holds the user's current delivery intent: how they mean work to be delivered right now, and why, so agents deliver work in the shape they expect. It is opt-in per project through `intent` in `.claude/ang.json`, and `validate` errors when the flag and the doc disagree. It pays off on product work built from shaky or unknown facts, where discovery dominates; on a contract working through a team's tickets it gets in the way, so `/bootstrap-repo` defaults to no doc. To switch it on later, the user asks any session to write it and set the flag; to switch it off, delete it and clear the flag.

- **It is the user's.** Agents keep it so every session can read it and so they are spared the upkeep. Agents help turn the user's thoughts into a revision written for agents to read; they never decide what it says.
- **It changes in any session the user revises it**, unlike the rest of 10k, because their intent can shift for reasons outside the repo.
- **It is checked on a schedule, not ad hoc.** `/retro` and `/curate-10k` play it back and ask whether it still holds; a yes updates `confirmed:`. Nothing else prompts a review. A *holds until* condition becomes a trigger only when it is checkable (`stage:`, `story:`, `after:`).
- **Shape**, after *commander's intent*, which is written so people can act sensibly when circumstances change. Frontmatter carries `confirmed: YYYY-MM-DD` (the date the user last confirmed it; `validate` requires it). Sections: Summary · The goal, and what reaching it looks like · Why we work this way · The stance · What it means for agents · Holds until · Related. State nothing that is true only today, such as the current edge; `ang-context-manager.mjs board status` holds that.
