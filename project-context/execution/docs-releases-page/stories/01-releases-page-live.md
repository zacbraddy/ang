# Releases page live on the docs site

## Summary
This is the whole epic in one story (d7). The scope is config, one workflow and doc edits, and shaping spiked both risky halves green. The story lifts the spike files into `docs/` and `.github/workflows/`. The notes template loses its h1 so each release nests under the plugin's version heading. The release process and 10k are updated to match.

## Outcome
- A token build of `docs/` serves `/releases/`, built by starlight-changelogs 0.7.2 from published stable GitHub Releases. It shows one newest-first page and one "Releases" sidebar entry. The page stays empty until v1.0.0 is published (d2).
- Publishing a release runs `redeploy-docs-on-release.yml`, which dispatches `deploy-docs.yml` on main (d3).
- The notes template and the v1-launch-notes trigger use the new heading shape: a bold `**🚀 {theme}**` line and `###` sections (k12).
- `/cut-release` step 8 checks, for stable tags, that the redeploy went green and that the page lists the tag.
- ADR 0008, project-structure and the 10k context view describe the new setup (d4).

## Rough scope
Do it in the [plan's sequencing](../plan.md#approach-and-sequencing), which covers all nine [scope rows](../plan.md#scope):
1. Template and trigger: `releases/notes/README.md`, `project-context/triggers/v1-launch-notes.md`.
2. Plugin on the site: `docs/package.json` with the exact pin and the `overrides` entry, a regenerated lockfile, `content.config.ts`, `astro.config.mjs`, and the `GITHUB_TOKEN` env on `deploy-docs.yml`'s build step.
3. Redeploy workflow: copy the [spike file](../origins/docs-releases-page/spikes/release-redeploy/workflows/redeploy-docs-on-release.yml) as is.
4. Release process and 10k: `/cut-release` step 8, ADR 0008, `10k/technical/project-structure.md`, `10k/technical/architecture/1-context.md`.

The exact keys, steps and headings are in [C4 code](../c4/4-code.md). The spike files for the site are in [spikes/starlight-changelogs/site](../origins/docs-releases-page/spikes/starlight-changelogs/site/).

Out of scope: see the [plan's Out of scope](../plan.md#out-of-scope). That covers RCs, prose above the list, rewriting rc notes, quick-start/upgrading links (d5), `llms.txt`, and new tests (d6).

## Done when
- The local build passes: `GITHUB_TOKEN=$(gh auth token) npm run build` in `docs/` is green, and `/releases/` has a title and version finder.
- `npm ls astro` in `docs/` shows a single Astro, 7.4.12.
- `npm run format:check` at the repo root passes.
- All nine scope rows are changed as [C4 code](../c4/4-code.md) describes.

The first CI deploy and the v1.0.0 end-to-end check happen after this story. The new cut-release check covers the second.

## Acceptance criteria
- Given no stable release is published, when `docs/` builds with a token, then `dist/releases/index.html` exists with the "Releases" title and version finder, and the build only warns that the changelogs collection is empty.
- Given the built site, when any page loads, then the sidebar ends with one "Releases" link to `/ang/releases/`, after the five autogenerated groups.
- Given a published stable release (a draft or an `-rc.` pre-release doesn't count), when the docs build, then the page lists it under its version heading, newest first, on one page.
- Given a release body in the new template shape, when it renders, then the page has one h1 and the body's `###` sections nest under the version heading.
- Given Zac publishes a release, when `redeploy-docs-on-release.yml` runs, then it dispatches `deploy-docs.yml` on `main`, not on the tag ref.
- Given `docs/package-lock.json` without the override, when `npm i` runs, then Astro 5 gets nested and config load crashes. The lockfile must record the override, and `npm ls astro` is the check.
- Given the GitHub API fails at build, when a production build runs, then the build fails and the deploy job is skipped, so the live site stays as it was.
- Given `/cut-release` reaches step 8 for a stable tag, when the redeploy run failed or the page lacks the tag, then the summary lists it as left, with the `gh workflow run deploy-docs.yml --ref main` fix. For an `-rc.` tag the check is skipped.

## Test plan
- **Unit / integration / E2E:** none new (d6). Everything is config, workflow and docs, which `engineering-defaults.md` says not to test. No existing test reads `docs/`, `.github/workflows/` or `releases/notes/`, so `npm test` stays as it is.
- **Checks instead:**
  - Local build: `GITHUB_TOKEN=$(gh auth token) npm run build` in `docs/`. Look at `dist/releases/index.html` for the title and finder, and at any page for the sidebar entry.
  - `npm ls astro` in `docs/`: one Astro.
  - The existing link crawl of `docs/dist/` (project-structure's docs dragons) stays clean.
  - Repo root: `npm run lint` and `npm run format:check`. Prettier skips `docs/`, `releases/`, `project-context/` and `*.md`, so it checks the new workflow file only. Match the surrounding style by hand everywhere else.
- **Deliberately not tested:** the plugin's rendering, filtering and pagination (library behaviour), the redeploy dispatch (spiked green, and the cut-release check covers it at v1.0.0), and template heading shape.

## Implementation notes
Follow the [plan's sequencing](../plan.md#approach-and-sequencing); the exact keys are in [C4 code](../c4/4-code.md).
- **Template (row 1):** `releases/notes/README.md` lines 9–32 are a fenced block. Replace the `# 🚀 Ang vX.Y.Z: {theme}` line with `**🚀 {theme}**` as the body's first line, keep the intro after it, and change the four `##` sections (✨ What's new, 🔀 What changes for you, 🐛 Fixes, 🔗 Changes in this release) to `###`. Update any surrounding prose that names the h1. Leave `v1.0.0-rc.1.md` and `v1.0.0-rc.2.md` alone.
- **Trigger (row 2):** `v1-launch-notes.md` only says "emoji per heading" today (line 18). Add that v1.0.0's notes follow the template's shape: a bold theme line, no h1, `###` sections.
- **Docs site (rows 3–5):** add the spike's new lines to `docs/package.json`, `docs/src/content.config.ts` and `docs/astro.config.mjs`, keeping each file's current formatting. The spike's [`package.json`](../origins/docs-releases-page/spikes/starlight-changelogs/site/package.json), [`content.config.ts`](../origins/docs-releases-page/spikes/starlight-changelogs/site/content.config.ts) and [`astro.config.mjs`](../origins/docs-releases-page/spikes/starlight-changelogs/site/astro.config.mjs) also reformat lines that don't change, so don't copy them over. The new lines are: the pin and `overrides` block; the loader import and `changelogs` collection; and the plugin import, `starlightChangelogs()` in `plugins`, and the `makeChangelogsSidebarLinks` spread last in `sidebar`. Then run `npm i` in `docs/` so the lockfile records the override.
- **Deploy workflow (row 6):** add `env: { GITHUB_TOKEN: ${{ github.token }} }` (block form) to the `withastro/action@v6` step. Permissions stay as they are: `contents: read` is enough, and it hides drafts (k9).
- **Redeploy workflow (row 7):** copy the [spike file](../origins/docs-releases-page/spikes/release-redeploy/workflows/redeploy-docs-on-release.yml) to `.github/workflows/redeploy-docs-on-release.yml` as is. Its `name` must be "Redeploy docs on release", which the cut-release check refers to.
- **/cut-release (row 8):** `.claude/skills/cut-release/SKILL.md` is a repo-only skill, not under `src/`. Add a **Docs releases page** bullet to step 8 next to **Latest**, for a tag without `-rc.`:
  - The latest "Redeploy docs on release" run, and the `deploy-docs` run it started, are green (`gh run list --workflow redeploy-docs-on-release.yml --limit 1`, then the same for `deploy-docs.yml`).
  - `https://zacbraddy.github.io/ang/releases/` lists `<tag>`.
  - On a miss, the fix is `gh workflow run deploy-docs.yml --ref main`, and the step's "what's left" line names it.
- **10k (row 9):**
  - ADR 0008: line 15's two allowed add-ons become three, with the override and why it exists. Lines 9 and 24 gain the release-publish redeploy from main. The sidebar is the autogenerated folders plus one Releases entry. The build reads GitHub Releases with a read token, and the page shows stable releases only.
  - `project-structure.md`: a row for the new workflow; line 28's `deploy-docs.yml` row names its second trigger, the dispatch from the redeploy workflow.
  - `architecture/1-context.md`: lines 9, 25 and 51 gain the release-publish build, and the docs site reads the GitHub Releases API.
- **Edge cases:** before v1.0.0 the page is empty by design (d2), so add no empty state or prose. A build without `GITHUB_TOKEN` still works locally, but unauthenticated reads can hit rate limits.
- **Out of scope:** the plan's list, plus a `releases/notes/**` path trigger on `deploy-docs.yml`, since the page reads GitHub release bodies, not the notes files.
