# What is Ang?

## Overview

Ang is an framework built for use within Claude code and with features that allow it to be enriched by being used within the Agentic Development Environment (ADE) Orca who's core purpose is to facilitate a robust yet malleable AI-assisted software development workflow in way that supports all aspects of software development. What I mean by it supporting all aspects of software development is that it doesn't simply support the technical delivery of software solutions although it most certainly does! But Ang also considers the entirety of the software product delivery life cycle where required including marketing, sales, project management, competitor intelligence, etc.

Although Ang provides a wide range of capabilities to support the delivery of software products, a user of Ang need not be concerned that Ang is attempting to be another of those Agentic development frameworks that attempts to be "all singing, all dancing" in it's documentation, but on first use, explodes on impact with a real agent as the agent proudly produces gibberish and pats itself on the back for a job well done after it's context window is downed in framework related tokens before the first command is ever sent by the user.

There's a lot that will be said about how this achieved as this document proceeds but at it's very core there are two main principles at work here that help Ang to achieve these results:

1. Ang **does not** drive the development of the software it creates, you, the human does. This is an AI-**assisted** development framework, not a software vibe-bro software factory where you fucking telling Jarvis to tell your "Chief of Staff agent" Derrick to fire your engineering department agents and then buy another fucking tesla or whatever!
2. At all stages of development Ang's main objective is remain lean.

There you go, I said it was going to be unstructured stream of consciousness! I forgot to even talk about the name, well I ain't editing now so you'll just have to deal with it now. Ang is a three-letter acronym because, as we all know, all the best things in tech are. ANG stands for Avoid Naval Gazing. This was because, ultimately, I was finding that all the agentic development frameworks that I was experimenting with and using to power my day-to-day development efforts, when looked at objectively, only seemed to REALLY differ by the length of time it took for them to devolve into a state of paralysis caused by each agent session adding to the heaping pile of "we definitely need to consider this" edge cases until agents would be stuck forever over-speccing, over-engineering and ultimately never making any progress at all towards the goals of the software project itself! After several failures with several popular frameworks ending in this way I reasoned that the only way I could avoid having another software project crash and burn under the heaping weight of it's own girthy context library is to find or build a framework that avoided all this naval gazing by agents at all costs. Thus: Avoid Naval Gazing. As a fun aside, Aang is a character from the Anime Avatar, so I would like to add a fun little tag line to complete the name:

> Ang (Avoid Naval Gazing)  
> The Last Software Bender, you'll ever need 

## My history of use of AI in developing software i.e. what lead up to me building Ang

Although my experience with AI assisted software development might not be directly or entirely relevant to the work that we'll be doing in this repo I think it's important context to provide none-the-less and may prove to be somewhat relevant to some parts so probably worth going through.

### In the beginning - simple agentic usage

I got my start working with LLMs in around late 2022/early 2023 when Jetbrains (who I've been a user and advocate of their products for a long time) released Junie into their IDEs. With LLMs starting to gain traction in the wider software development community's zeitgeist I decided that it was time, once again in my career, to see what all the fuss was about with this new tool. I began using it as essentially just a built in way to ask questions like I would in the ChatGPT web interface but without having to copy paste code for context. I'd spend many hours prompting in a single chat session, often returning to the same chat session the next morning and continuing to talk to the context addled agent.

Unsurprisingly at this point I had sufficiently convinced myself that although AI may be useful so some minor things that ultimately rumours of the death of the software developer were greatly exaggerated! Still I had wondered how the hype managed to continue despite it crashing and burning so spectacularly. Luckily I've reached the point in my career where I've grown enough humility to know that although sometimes my original ideas might be novel even when they fly in the face of accepted conventional wisdom, far more often it's me that is that is problem! So I went about researching how to make these agents more useful. I discovered the concept of system prompts etc. and found the Junie functionality that would allow me to inject context into every session. Then I went about building a **gigantic** markdown file that covered every single convention, practice, thought and theory that I subscribed to in software development with the hope that I'd be creating an agent unfathomably customised to work in exactly the ways I wanted it to. Essentially my goal was to create an agentic clone of myself, what I created was an agent whose psychotic nature was only rivalled by it's ineptitude!

At this point I had all but given up on Junie but Cursor was taking off at that time and I was yet to experiment with the claude web UI. To avoid this part getting too long in the tooth the short review here is that I basically tried to reattempt the whole "Zac as an agent" idea using projects in Claude Web and found this just resulted in the same context soaked agents that served to do nothing but burn tokens, shock horror, I know! However Cursor became my first success story in agentic development. I found that Cursor supported exactly the type of development I needed it to at my stage of discovery of AI-assisted development. I found the AI assisted Intellisense/tab editing to feel like absolutely magic and using cursor helped me to understand the concept of windows so I was opening more sessions and keeping tasks discrete and self contained. At this point I was essentially keeping the entire development process in my head but directing agents at whatever task I knew was next in line to be done to achieve whatever I was working on at the time.

This was good but, as I now know, this was hardly what would be considered a true AI-assisted software development workflow. It was around this time that only a month or so before that time that SpecKit had been released.

### Feet under the desk - Speckit

Speckit was somewhat of a revelation to me as it was largely addressing a lot of the issues that I described my battles with in the previous section. This was a way to provide an agent with an overarching project/delivery goal while allowing each individual agent session to remain focused on whatever individual element of the software delivery it was to be focused on delivering against. Each session could remain narrowly focused on what it needed to deliver while also allowing for any decisions to be made within the task to be guided through the lens of the high level objective of what was being worked on. Not only did this greatly aid in the effectiveness I was able to squeeze out of each agent session but it also formalised into the framework the overarching workflow that I was currently keeping in my head and hand cranking in my work with Cursor.

I did find however that Speckit did seem to lean pretty heavily towards investing a lot into doing a lot of high-level planning and then essentially getting to the implementation step and having the developer driving be expected to just "hit the go button", go get a coffee and then expect to return to working software. This caused the effectiveness of the framework under my direction to creak, I don't work in a MANGA company, quite the opposite, the majority of the work I do is with early stage startups or at most companies that would be considered SMEs. In these environments the sorts of things your can expect to be throwing agents is less of a "perfectly curated and specified JIRA ticket" type environment and more of a "specs scribbled on a napkin and even what's written we aren't sure about" type deal. This would cause two things to happen that Speckit found very difficult to deal with: 

1. These loose specifications often sounded simple on the surface at the beginning of the speckit workflow but as you progressed through the speccing and planning stages I'd discover that we'd **obviously** bitten off more than we could chew when it came to what we were trying to achieve and really it'd be more appropriate to break the whole thing down even further into delivery stages. But by the time we got there my options were to continue with the "hit the go button approach" which at the time was outside of LLMs capabilities to sensibly achieve in the single session that SpecKit wanted to do it in. This was because this was a time before agent harnesses had introduced features to so easily operate with sub agents and the like so the **entire** epic would need to be delivered within a single (much small back then) context window.
2. Often "discovery" would be happening during implementation, it was impractical at best, impossible often, to be able to spec any one project to the degree where you'd be able to reliably avoid scenarios where half way through working through the implementation tasks I'd discover that we would need to completely change the direction we were headed with the implementation.

By this time though I was starting to get pretty comfortable with using AI to drive my dev workflow and could see the value inherent in investing in increasing it's prevalence and effectiveness within my tool chain. Speckit was so very close to what I needed to succeed and given that it ran entirely on simple markdown files and it was open source after all, so I decided that the best course of action would be to cut myself a copy of it and modify it to better suit my needs. So that's when I open sourced my [ai-software-dev-workbench](https://github.com/zacbraddy/ai-software-dev-workbench) my first attempt at a software dev framework and for the most part it I found some decent success with it and used it for quite some time.

The main modification that I made to the original spec kit was in the implementation stage. The how planning, scoping and speccing stages were left largely intact and unmodified but when it got to the implementation I had changed the workflow from a single agent looping through the process of writing stories, implementing them and then reviewing them from top to bottom in a single session, instead I would manually kick of each of these steps for each of the stories that were planned each within their own sessions. I found that this helped in that three separate agents would be responsible for each step of each story allowing there to be three agents "checking each other's homework" rather than a single agent confidently presenting you a work that it claimed was the single best thing that has ever been done in the history of software development, regardless of the realities of the actual quality of the solution it had just built. I had discovered at this early stage that agents seem to be much happier to be critical of code that it didn't write than anything it creates itself. Humility seems to remain a uniquely human state of being!

Because the implementation step was now a step-by-step process with we involved every step of the way this also allowed for me to be involved throughout the process so that if I found that we were in the process of "discovering" that we were headed in the wrong direction I was there to rip the ebrake and start course correcting. Although this course correcting was not something I was finding myself having to do on too regular a basis it was, unfortunately, happening at that incredibly annoying frequency that borders between it not really happening frequently enough to justify the time investment of codifying the process in my workbench officially but happening frequently enough that the time wasted on these course corrections was real pain felt and real slow down when it came to delivery schedules.

One thought limitation that I couldn't help but notice with Speckit was that it was fantastic at delivering medium to large pieces of work like new features and/or modifying or otherwise migrating features or architecture within a software product, but when it came to smaller adhoc work it fucking sucked! Larger pieces of work it did extremely well with directing and helping agents to produce great work that really did accelerate the delivery of those large pieces. But if you had your CEO come to you asking to change a button to cornflower blue or a customer support engineer begging you to just do a quick lil hot-fix on a bug for a super important client there was just no way that you could justify pickup the ai software dev workbench for these tasks. The ceremony required and time spent having agents pour over every edge case and possible knock on effect as part of the planning and speccing process would often dwarf the amount of time it would take to just raw dog some prompts to an unbriefed agent or possibly even just hand code a fix like a fucking caveman!

It was around this time that I found BMAD and it represented a very impressive jump in the direction that I was already heading.

### BMy first grown up AI dev workflow BMAD?

[BMAD](https://github.com/bmad-code-org/BMAD-METHOD) **really** impressed me when I first discovered. First, it was extremely validating that the direction that I had been heading in with my software dev workbench! But also, this was proof that I was not the own dev out there that had come across the challenges that I did with the workflows available at the time and tried to solve them in the way I did, but more than all this the problems that were on my horizon with the development of my software development workbench like course correction and considerations around being able to escape the high level of ceremony required by the framework when you needed to do just do something small but still being supported by the framework in these endeavours had all already been considered and built. As if this wasn't enough a metric fuck tonne of other things had been considered and built that weren't even things that had occurred to me! Like having different specific agent personas with specialisations that you could bring into a session to poke at an ideas from multiple different angles. There's was a lot more that I was impressed by but I think I've done enough glazing of BMAD at this point, you get the idea.

On discovering BMAD my direction was clear and set. Having worked for so long in startups a lot of my successes in my development endeavours have taught me that when delivery needs to be king as it so often is in the work that I do that you are best served by having a preference to "buying" over "building" when given the choice. Up to the advent of LLMs in software development I've been firmly of the opinion that there's next to no point in spinning up your own way of doing things when an open source project exists that produces even 80% of what you're trying to achieve because even if you have to hand roll that 20% when you're working in startups your job is not to create novel solutions to the technical problems that you need to solve to support the internals of the software, not a single user gives a single shit about that. Your job is to write software that delivers the value that the business you're working for exists to deliver! To be fair this is really true in all sizes of business but it's most prominent and obvious when you're working in an environment where if you don't deliver that value on Friday there might not be a company to work at on Monday! In accepting that reality, you implicitly must accept the reality that you have absolutely no hope of being able to replicate that 80% of what you're trying to achieve in a way that would even hold a candle to what a team of open sourced developers who's only focus is solving that problem than you, to whom the problem only represents a small part of a much wider picture! All this is to say that BMAD represented a solution to about 200% of the solution that my ai software dev workbench, so the direction I needed to take was as clear as day; I dropped my work bench immediately and started using BMAD as my core driver for AI-assisted development.

This continued for a decent amount of time and for the most part I was fairly happy. I did still get the distinct feeling that BMAD was still a bit too rich in it's ceremony when it came to speccing out the large pieces of work and it frequently didn't even result in projects that were able to reliably avoid a course correction! That said having the course correct command there to manage when we "discovered" that we were headed in the wrong direction was a very welcome addition. On top of that having the bmad-quick-dev command for adhoc tasks was a brilliant little feature to have in my toolbox. For the most part I was finding that BMAD did a pretty good job of supporting the whole of my day to day development, despite it's few minor downsides.

The only time that I found BMAD started to creak under the my demands of it was when I returned to the world of contracting. For the majority of my journey with AI-assisted development I had been working in permanent employment as a full time worker within a wider team as I was taking a break from contracting at the time. In these environments even though the degree to which the work to be done was defined two things were taken as givens when working with BMAD agents:

1. Even if there were unknowns inherent in the specific project you were directing BMAD agents at. The high level "north star" type direction was known and set outside of the BMAD framework. You were working within a company that delivered software that aimed itself at solving X problem for a Y customer base. The unknowns were still unknowns but they would some what bounded in scope and localised to the work being done, there were largely no unknown that would unilaterally affect ever aspect of the development process.
2. Although there were agents provided in BMAD that were scoped to address the wider landscape of delivering software, considering not only the business elements of delivering software but also things like UI design, archtecture and QA, I found that these agents were more in a position to validate positions you already had rather than help guide you through the process of understanding and decision making where things are more uncertain and your knowledge of that part of the field is less than expert. Essentially, it kind of felt like BMAD was extremely good at driving the technical delivery of software and had gone a step further to consider the other elements of software product delivery but only to the bounds and extent that when working in a team you'd be able to keep the considerations already put in place by the other members of the wider team within the company you were working in were kept in focus by agents that were delivering the software, but it still expected you  to have a firm idea of what the baseline expectations of these non-technical elements of the project are yourself and if you didn't your options were to rely on LLM reasoning or.....idk...

Moving into contracting meant these creaks showed both in the fact that I was now solely managing my contracting business but also I had ambitions and aspirations to slowly start shifting the direction of the business away from contracting and more towards making the business one that creates and selling software products. This meant that I could no longer stay safely within my technical bubble when it came to delivering products, only paying lip service to the other elements like marketing, sales or even just product ideas! I either needed to come to BMAD with these things decided or I need to find a framework that supported me while I onboarded into all the new roles that I'd have to now embody within the software development process. More than that I'd have to embody them to a degree of expertise that I'd have to come preloaded with my own opinions and preferences so I could confidentally make any decision that BMAD might need my steer on. Supporting both the onboarding effort while also being expected to be able to function in the role to high level of expertise required felt like a task that was going to be beyond me so I needed to start searching for a framework that would be able to support me in trying to make both of these things true to a high enough degree that I could be successful in my endeavours of changing We Right Code into a proper software business.

## Swing and a miss - The Matt Pocock Skill chain

It was then that I discovered just how late I was to the party on the [Matt Pocock](https://www.aihero.dev/skills) skill chain! I'm not going to spend a huge amount of time on this section because I do think that these skills are really well built and ultimately I don't think my failure to see results from these was entirely caused by the skill chain itself, I've seen and heard of people who are using them to great effect and Matt has **obvious** invested a great amount of time and effort to make them supremely useful and effective. If I'm being fair and honest I think that, really, the ask I was making of them, as described at the end of the last section was perhaps just too great for **any** framework not built to support my specific needs to support, as evidenced by my decision to build Ang in the first place which had these requirements and others baked into it's very reason for existing! More on that in the next section though.

The reason for my interest in this skill chain was particularly around the wayfinder skill which I saw a video on youtube of Matt giving a talk on. It seemed to aim to address the problems that I've described in the last section in the way that you would provide it with a high level idea with **lots** of unknowns which he referred to in the skill as fog. The goal with each agent session was not necessarily to boil the ocean trying to solve for the entire problem at once because:

1. A problem with so many unknowns is likely going to balloon as unknowns act like a hydra revealing more unknowns each time an answer is revealed. So the concept of being able to solve the whole thing in a single session was completely unfeasible for a single agent session to solve for.
2. Because unknowns will often reveal further unknowns, often your own direction is required to know what each answer discovers means in the context of the project you're working on. Every time new information is revealed if you aren't involved in providing steer for what that information means in the context of what you're working on then you are leaving yourself at the mercy of agent reasoning to ensure you remain on track.

Wayfinder seemed to provide a good answer for managing these issues as with each session it would be provided with the context of the high level goal that you were trying to achieve to keep the session focused but also would only focus on progressing one step further into the unknown, which both kept accuracy high as the workload remained manageable and also kept you along for the ride of discovery which helped with the onboarding issue described in the last section.

I also really liked how "grown up" the wayfinder skill felt in the way that it managed it's context within github issues instead of markdown files. It really made the whole process feel like it was much better documented and managed. Unfortunately, and paradoxically the main problem that I found in using wayfinder was actually within it's context management. The main problem I found with wayfinder was somewhat of a "Mr Meeseeks" sort of problem. While you were tasked with setting the "north star" for the thing you were trying to make less opaque and amorphous there was still somewhat of an expectation by the skill chain that the ideas that you were tasking it at very least had somewhat of a discrete result, or destination that could be stated as being measurably arrived at. But for the majority of the problems that was needing wayfinder to help me navigate resulted in agent after "I'm a bit of a stickler Meeseeks" agent would iterated on trying to solve the problem into the void.

I was finding that with each session context was growing as another edge case was lumped on the heaping pile of fog that future agents would then have to wade through. It seemed that while the agents were excellent at finding things you hadn't thought of but once those unknowns entered the context of the wayfinder map you'd then find yourself wrestling with every subsequent agent pleading with them that solving for every tiny eventuality that could ever happen was far less important than arriving at our destination even if it meant that we were would necessarily have to arrive at the destination with some things still not in strikingly focused detail. It's true in startups that you sometimes your success is predicated on being able to move forward **despite** not having the full context of the direction you're headed and just resign yourself to learning as you go and/or shifting direction as the answers to whatever remaining unknowns reveal themselves naturally as a by product of your progress. This is doubly true when you're a solo dev company trying to come up with good ideas for products you can build and sell! Unfortunately, wayfinder was just not geared up to be able to managed that level of ambiguity and because it's task as set by the skill was to continue until all unknowns were known, it couldn't bring itself to adhere to the realities that arriving at the destination with 80% of the landscape revealed was far more important to the success of the process than never arriving there chasing the ellusive 100% vision of that landscape.

So the result was that in the times I was using/experimenting with the wayfinder skill in the handful of different projects that I tried to introduce it to is that the context held with the map and it's child issues ended up just expanding and expanding until, as I had seen in other projects, it ballooned to the point where agents stopped being even close to helpful. The just started losing track of the direction we were headed, going off on long complicated tangents for next to no perceivable benefit and eventually I had to accept defeat and admit that as promising as the it seemed that wayfinder would represent my next "BMAD-style" discovery of a tool that was exactly what I was looking for without building it and I had to move back to migrate the projects I had used wayfinder in back to BMAD to continue with them.

## My motivations for building Ang

Having now tested the limits of the frameworks mentioned above I was at the point where I was beginning to realise that my hopes of being able to find a framework that could flex to my specific requirements with any great success. While the frameworks that I tried were all great in their own specific ways all of them failed me in one way or another and in ways that would repeat despite having tried throwing them at multiple different shaped projects. In the past with the "buy over build" mentality that I've mentioned that I carry with me in my work my answer would have been just to mix the frameworks in my efforts to allow them to cover each others' short comings. But the difficulty with doing that in this case due to the different ways that the different frameworks managed their context. To achieve a multi framework type scenario would require me to modify each of them to not only be aware of how each other but also I'd need to provide some for of interop layer to allow them all to work together which would seem, at that point, and considering we now live in an age of AI to be more work than simply just making my own framework from scratch, it would seem that it was time to build! After all at this point I'd collected a number of year of experience working with different AI-assisted software development frameworks, I only mentioned three above but those only represent the ones that I thought were worth mentioning as they represented significant improvements to my workflow and/or had features relevant to the how and why of me building Ang.

From what I had seen of the frameworks I'd used and how they failed me the main gaps that Ang would need to cover to be considered a success were:

- It should not be complex or heavy handed in it's processes.
- The context created and curated should be done so carefully.
- All agents should work on the understanding that they are **most definitely not** in charge!
- The framework itself need to be malleable easily being able to bend itself to remain useful given whatever environment and software project it finds itself in
- Agents should understand that if I ask it to guide me through a topic that I don't have expertise in that I could not give a single shit about what it can reason about the topic, I only care about what true and real experts can teach me.

With those elements in mind I began work on the first cut of Ang. I mentioned above that when wayfinder failed I reverted back to BMAD on all my projects. At the time I had two projects on wayfinder and 1 on BMAD. So what I did is I started the Ang build in one wayfinder repo with the view to it's first task being to migrate me away from wayfinder on to Ang, this was a less important project so was a decent enough test bed for the first proving out of Ang. The other wayfinder project I did a similar migration project but driven by BMAD. And my third and most important project I left on BMAD as that was the most reliable framework I knew of at that point in time.

As I started building Ang I impressed upon the agents helping me build it the list of requirements above particularly, as it was most relevant to this early build of Ang, the point that it should remain as light weight as possible. The goal was not to build an all signing, all dancing framework in this first iteration. In fact our goal should be to build as little as possible to reasonably start using Ang. This necessitated one of Ang's very early features, being a workflow improvement. The concept was that if I was going to begin Ang as an extremely bare bones framework that it would be likely that I'd find the bounds of it's abilities very early in it's lifetime and at that point I didn't want to have to stop dead the development work I was working on in my product to begin tinkering on my lil framework toy. To facilitate this the workflow improvement would gain two early features, the first was a skill that would have agent's looking out for friction that it sees when it's working through a session as an Ang agent and at the end of the session suggest softly to me that I might like to raise a workflow improvement so that I can avoid similar friction in the future. I say the suggestion was soft because I didn't want agents nagging me every round of every session with each agent desperately trying to over-engineer Ang in every round. That flew in the face of what I was trying to achieve with Ang in the first place! The second part of this feature would be a skill that the agent would use if I agreed that the friction needed to be address. With that skill the agent could create a workflow improvement document based on the context of the session and what went wrong within it. This avoided me then having to fix the friction within whatever session noticed it in as that session had been focused on actioning whatever Ang task it was set to complete and presumably it's context window had been exhausted with performing that task. But equally I didn't want to have to repeat the entire story of what went wrong to another agent in a new session. So by raising this document I was then able to start a new session and with a fresh context window another agent to focus intently on solving the issue. In this way I was always able to decide which additional features made their way to Ang without being bullied by agents to do so. Equally when I did want a new feature included I didn't have to invest a heap of effort that work could be farmed off a new and capable agent to be completed for me allowing me not to lose too much time on there framework modifications and I could remain focused on delivering the software that I wanted to.

With these things in place I was able to relatively easily and very successfully perform the migration to Ang. I continued working with and continued to be extremely happy with the results. It was at that time that the other project I had migrated away from wayfinder and to BMAD had it's agents starting to lose control of it's context library so I decided to give Ang it's second test. I migrated the second BMAD repo to Ang and it was pretty pain free and worked just as successfully. After a little more time working both the Ang repos I decided that actually it might be time to properly put Ang to the test. My final BMAD repo with my most important and complex project was then migrated to Ang using Ang and was done so successfully! Since then I've been developing entirely using Ang, adding minor workflow improvements as I went but ultimately keeping it to a minimal feature set and I have to say I've never been so effective and happy with the result than with any other framework I've ever tried!

At this point Ang has been battle tested as much as can be reasonably expected considering it's author has been it's only user thus far and it was now that I began entertaining the idea of open sourcing it. I did have mixed feelings/ideas around whether or not I'd open source it for two reasons. First and foremost, I don't really have the time to dedicate to being a proper open source maintainer! But perhaps more importantly Ang had been built in a way that was extremely bespoke to my own workflow. This presented a difficulty for two reasons:

1. It was built so bespoke because I was the main user of it! I didn't want to modify it so that I could homogenise it for a wider user base I wanted what I had, it was built that way because that's the way I wanted it!
2. Given it was so bespoke, was there any point in open sourcing it anyway? It could be a complete waste of time as open sourcing it implied that people would want to be held to my own opinionated way of working.

The reason I did end up deciding to open source it after all was that really the core first principles behind the way I had been building Ang and the way I had committed to guide it's implementation actually inherently addressed both of the issues listed above!

Although the framework is built bespoke for me and is fairly opinionated in it's operation where I've chosen to allow it to be opinionated, I also committed to keeping Ang as light weight as possible and as light touch in terms of process as possible. What that meant is that although I found Ang extremely useful to my workflow, the reality is that it really only represents an extremely vanilla software development framework. This not only meant that it is likely fairly homogenised ready for a wider user base out the box, but when you pair that with the concept of workflow improvements and the way that the light touch leads to fairly malleable agents out the box means that even if Ang out the box isn't a perfect fit for someone, it's is **well** within reasonable bounds for them to raise whatever workflow improvement they wanted so that they could make their own improvements and have exactly what they wanted!

This solidified in my mind what Ang was, it was "The last software bender". It's and open source AI-assisted software development framework that it's light weight and usable out the box, but when you find limits that are bespoke to your own development process it comes built in with the tools that allow you to bend and shape it in a way that keeps it useful in the face of things that it hasn't been built specifically to do. Ang isn't a framework like BMAD or Speckit or Wayfinder which give you a complete "Sourdough bread" it's more of a "sourdough starter" on which you can build your own perfectly tailored master piece.

This also has the knock on effect of avoiding me having to become a proper open source maintainer as Ang is not something that is intended to be built on and improved ad infinitum. It's not in an open repo with the hopes that every person and their dog would be raising PRs against it requesting the next big feature be added to it's ever growing roster of features. The idea is, if you want to use Ang, go for it. If you want it do something slightly differently, fucking go for it mate! You don't need to tell me about it though. Fork Ang if you want or even just copy the source files and get to work making it your own, you don't need to tell me about it. And I'd be doing the same thing, I'd be keeping the features that I build with the workflow improvements to a bare minimum only introducing features that I can see would provide truly universal benefit but ultimately keeping Ang's actual feature set lean and as unopinionated as possible so that it can remain useful as a start for anyone to build their **own** software development process that is perfectly tailored to **exactly** what they're trying to do!

## Ang's first principles

It has helped me quite a bit as I've been building on and improving Ang to keep in mind my reasons for having embarked on the journey to build it in the first place as doing so has helped me to remain consistent when making decisions about what I will and will not build out to address friction in the workflow when I encounter it. I've come to refer to these as "Ang's first principles" and I refer to them whenever I'm making meta decisions about the framework. What it should and shouldn't be. What I would and wouldn't like to see it become. For what purposes it does or doesn't exist to serve. Until now they've existed entirely within my head but I think it's worth stating them outright as part of open-sourcing it, both so I can finally be clear with myself but also as I will necessarily need to be communicating these to potential users of Ang to help them understand whether it might be something they'd like to try themselves (or not, I guess...).

I've listed them below in order of highest priority to lowest. Each are paramount to the success of the framework, it should be said, the priority is not to suggest that there is or will be any scenarios in which we shouldn't be endeavouring to honour each and all of these first principles. But the priority order more signifies which of them that I think are most important to the success of the framework and what I think makes it so great, for me at least but hopefully for other users of the framework as well.

### 1. Ang works out. It's lean and must always remain so.

Having used a number of frameworks for AI-assisted development as well has trying my hand at building my own workflows a few times as well, I have been able to observe plenty of times where they've been a great force multiplier and delivered real value to the process of building software products, both in the speed in which it is able to to be delivered as well as the quality of the end results. Having had a decently full and rich career before the advent of wide spread LLM usage in software development I can tell you that some of the things I've been able to achieve through the use of LLMs in my software development workflow would absolutely have been possible and within my capabilities to achieve without them, I can say that with no doubt. But I can state with equal confidence that I would never have been able to achieve them to the same standard **and** speed without LLM assistance. It ultimately comes down to the classic Fast &lt;-&gt; Good &lt;-&gt; Cheap problem where you can only choose 2 in any delivery scenario. Without LLMs I could definitely deliver the same product as quickly as I did with an LLM but the quality would not have been to as high a standard. Equally I could have delivered something of the sort of quality it did but it would take me time to research, architect and ultimately achieve a similar result.

However let's not spend too much time glazing LLMs here! They are certainly **not** without their failings. Trade-off's have always existed in every aspect of software development and LLMs have done exactly **nothing** to change that! As I've said in the preamble for this section Ang's first principles exist to ensure that changes to Ang remain focused on ensure that the framework remains vigilant in avoiding falling into the same traps that other frameworks and workflows tend to that would cause them to suffer from the downsides of these trade-off's in an elevated way. The first one of these traps that I've seen framework after framework and workflow after workflow fall into repeated is that they simply try to manage too much, they try to remember too much, provide too many guard rails for agents and essentially hug the agents to death until the framework has essentially squeezed all the usefulness out of the LLM they're using as the engine of their entire framework. The authors of these frameworks are obviously and demonstrably very clever people. They, with no doubt in my mind, are able to fully and deeply understand the concept that they are building a system on what is, at it's core, a non-deterministic system. And yet, I so often see these frameworks, with each version release, take **another** step towards providing their users with a framework that will provide fully deterministic results in the way that the release notes essentially promise the user that the system will produce results that the user can rely on...every time. And look, we as the users are not blameless here either, I'm sure you've probably introduced an AI feature into your software products by now and had the talk with your business colleagues that they simply can't expect them to act in **exactly** the same way in every single scenario, that isn't what LLMs do! But here we are making the same demands of our frameworks!

On top of all of this, Anthropic themselves this year have released changes to their guidance on how to build tooling for use with Claude models whereby they have acknowledged that, yes, with past models some of the best ways to direct them have been by giving them clear guidance, essentially reducing the probabilistic nature of the results you can expect from one run to the next. But we're in 2026 now, models have improved in leaps and bounds and the reality is that they're so good now that the more directives and guard rails you give them the more you stand to miss out on the amazing results that the model could produce that you hadn't even considered! Essentially, the more direction and instruction you give the models, the more you're applying the ceiling of your own knowledge and capability in that moment.

And so, for Ang to acknowledge the power of modern models, and avoid the mistakes (at least as I've perceived) of other attempts at AI-assisted software development frameworks we adhere to the first principle that Ang must always remain lean. This first principle is applied as a cross cutting concern across the entire framework. It's  a higher level concept than any single part of the implementation of the framework as a guiding first principle should be but you can see it's affect in any number of areas of the implementation. This is to say, that the following sub sections are a list of some of the areas that I've applied the principle directly but that isn't to say that this is an exhaustive and complete list, rather it's just a sample of the places it's been applied provided as an example.

#### Lean Context

One the first things most people learn as they start bringing LLMs into their software development workflow is how to manage the model's context window in a way that allows us to ensure that the model remain's accurate, effective and useful. Don't lie, you also have been guilty at some point in your life decided that the rumours of the death of the software engineer were greatly exaggerated after scoffing at the ramblings of a sycophantic context addled agent who's incompetent, it would seem, is only overshadowed by the size of it's self-congratulatory nature! So, secure in the knowledge that the robots will never come for your job you close your chat session.....your....5......hour long.....chat session....

Guarding an agent's context window from exhaustion is, I believe, at the core of how you are able to reliably produce positive results from an agent. It's obvious I'm not alone in that believe because I'd say a pretty large majority of AI-assisted software development frameworks put this concept at the centre of how their frameworks work. It's pretty widely accepted that the way that we work with in these frameworks the majority of them adopting the practice of having separate sessions driving the tasks of writing a story, implementing a story and then reviewing a story's implementation, for example. Ang is no different in this regards it endeavours at every step to ensure that each agent session remains lean in it's focus and objectives for that session. Where Ang sets itself apart from some (not all frameworks) is that in each session whatever process is being executed the Ang process takes steps to actively protect the agent's context window in attempt to reserve as much of it as possible to be left available for tokens that drive the process towards success. This manifests itself  in encouraging agents to avoid the need to grab every possible piece of context available within the project's context library and the repo itself as par of any one session. Ang agent's context windows are further protected by encouraging them to use sub agents to this context for them rather than directly loading everything into context. With this summarised context from the sub agent the Ang agent driving the session is then able to better determine what pieces of context it will need in it's entirety to execute it's task rather than having to waste it's window on blinding determining this itself.

Another strategy that Ang uses to protect agent context windows, which from what I've observed in the AI-assisted software development landscape is fairly unique is that it treats the curation of the project's context library as a first class citizen. I've found that a great number of frameworks will progress work within a project ensuring that each individual agent session's context window isn't exhausted by moving the project forward in manageable steps and this, as I've mentioned, is a good practice. But in order for it to work the next session needs to be able to benefit from the knowledge and/or work that has been completed in any number of previous sessions. To facilitate this transfer of value between sessions most frameworks have each session produce markdown files, code artifacts, etc. that represents the results of the session's execution. Then rather than using the tokens needed to execute that task the next session only has to ingest the tokens that represent the results and then "take the baton" from there. This is all fine, Ang does this as well, that isn't where it sets itself apart. What is often ignored or, to be kind, overlooked is the inherent property of that workflow being that with each progressive session, the amount of artifacts available to that session grows and grows ad infinitum (in some cases). As the project progresses agent after agent is presented with an ever growing body of work to draw context from and what I've observed in these scenarios are agent's that become less and less capable of identifying which artifacts are **actually** valuable in executing against the single, tightly scoped, task that it is trying to perform within the project and wider framework. It seems in these scenarios that agent's start exhibiting some sort of "context FOMO" with each progessive session agent's seem to decide that in order to accurately execute against their task they require more and more of the available context library to achieve success! Or perhaps it's possible that each agent only requires the same percentage share of the context library but as the library grows this represents more and more wasted tokens to reach that percentage. Regardless of how we arrive there, the result is the same and undesirable; a framework that produces agents that become less and less effective as work on the project progresses.

Ang's approach to the curation of it's context library has been built with this problem in mind. It does this in two ways:

1. It keeps a project wide context library called 10k which helps brief each agent's session on the higher level (10k view, see what I did there?) concepts and realities that should be used to guide every agent session.
2. Each task that is worked through Ang's workflow (raw -&gt; ideas -&gt; shaping -&gt; planning -&gt; execution -&gt; retro) maintains it's own context that gets built up within each steps and previous steps context is kept within the task folder as development progresses so we still get the benefit of agent's working on a problem piece by piece and not "losing their place" or direction. However, each task maintains their own "sub-library", if you will, meaning that different tasks need not concern themselves with the context applicable to other in flight tasks.

Splitting the context in this way isn't the novel part though. The novel part is Ang's baked in preference to deleting or replacing elements of these context artifacts over keeping a history of the changes that have been over the lifetime of the project. Take the example where perhaps, during a project implementation you decide that instead of using prettier directly in your Typescript project you're going to bring in Eslint to widen the scope of your code quality capabilities in the repo. Many agents being driven by other framework will record this in what ever context artifacts they deem appropriate in a way that records the history of this in the project. They will waste tokens explaining to every future agent "we used to use prettier directly but now we've decided we want to widen our code quality capability so on DD-MM-YYYY we introduced and implemented ESLint and wired prettier through that". I think the intent here is to try and avoid the scenario where future agents try and reverse this decision so by recording it as a decision now the expectation is that future agents will read this context and avoid suggesting that as a move. But ultimately all we're really doing is burning tokens in every future agent session restating, what is now, a static fact about the project! In the same example scenario Ang agents would find what ever context about the code quality, perhaps it finds "We only use prettier not ESLint" and change it to "We use prettier and ESLint". No historical change log burning tokens, just facts that agents need to execute their task. Ang agents will be vigilant as they work to ensure that the 10k context library is a true and accurate snapshot of the realities of working within the repo they're working in and avoid as much as they can turning it into an ever growing journal of every little thing that has ever been done in the repo. This carries even to the ADRs it records, this may set some developers teeth on edge as it kind of flies in the face of what ADRs are trying to achieve. But the reality is that very few projects of substance are built outside of a git repo these days and at the end of the day, git itself exists as a ledger for the changes made in the codebase! Ang agents have been instructed to not be scared to use this to their advantage. If they really, truly, feel that some piece of the project's historical context is relevant to the task at hand then they are invited to reach into the git history to grab what they need but they are reminded the cases where these sort of actions stand to provide **real** value to the execution of their tasks are going to be extremely rare especially given that anything that currently lives as context housed in the current state of the file system is always kept in a state that accurately speaks to the truth of the state of the project and the intents of the work that is on going.

The way that Ang is able to make these assertions that the project's context library always speaks to the truth of the project's current realities is through it's context curation. We spoke above about the framework's preference for deletion and/or replacement of context over an ever growing list of changes over time and that's one way we implement this as an overarching principle but a more specific way this is achieved through the retro step of the process. During this step of the Ang workflow the agent executing the session is presented with the context sub-library that the task has built through the course of it's execution, which now is not only the stories but all the context artifacts generated by the previous steps, organised in a way that they are easily accessed, but equally, easily ignored by each successive step in the process. What the retro step now does is take in that context and scour it for elements of the task's execution that made changes or additions to the project that make it such that now the 10k project context no longer speaks to the reality of current state of the project. The retro agent is reminded that it's goal is not simply to summarise the task and throw the entire summary into 10k, it's instructed to look over the context and, again in order to protect the context windows of future agents, critically analyse which parts of the tasks execution **really** stand as important to be highlighted to each and every future agent. In this way we actively work to avoid the 10k becoming so large that it becomes no longer useful for future agents. Once the retro has performed this analysis and curation, it doesn't just merely archive the context sub-library of the task in a folder that all agents have been forced to **promise** to avoid opening, it outright deletes the entire context sub-library. Again, this doesn't mean that the sub-library is lost because we're presumably all working within a git repo! All it does is takes context which is now highly unlikely to provide any real benefit to future Ang agents and places a mild amount of friction such that future agents are less tempted to waste their context windows loading it in "just in case" like they seem to so frequently do when you leave context lying around in the project's file structure.

#### Lean tooling and guard rails

We won't delve too much into this topic here because it blends fairly heavily with the second principle but it's work meaning here because an overlap **does** exist here. As a first principle Ang attempts to stay as un-opinionated (as a framework can be while still remaining framework!) as to how things should be done. I'd say there are few minor features that I won't mention here as it doesn't really aid the discussion but I'd say the only **major** features it provides is the core workflow of how tasks are progressed, guidelines on how context should be managed, tools to support Ang users in making their own modifications so they can bake their own opinions in and make it your own, and the concept of workstreams to allow users to be supported in progressing multiple streams of work within the same project allowing them not only to reduce their own downtime by allowing a workflow where you can be typing prompts into one workstream agent session while waiting for the result to be produced in another, but also allowing for Ang to be used within a team environment where Ang agents are able to support help support opportunities for collaboration between team members through it's built in cross workstream messaging system.

That is more or less the entirety of Ang's feature set and I don't really have any plans for increasing that. The reasons for this apparent lack of ambition for the project is two-fold:

1. This helps Ang remain faithful to the other three first principles which we'll explore more in their respective sections, and; more relevant to this first principle
2. This helps avoid the scenario that I have observed in a number of other frameworks and workflows where their feature set's and guard rails have become so large that all usefulness is squeezed out of the agents. In the fact of a huge number of complex steps I've found that agents sometime get lost in a maze of procedures that they desperately and dogmatically attempt to adhere to at every step. Equally I've found that an excess of guard rails can hurt in a few ways. In the same ways as complex processes can cause agents to become less effective sometime you'll find agent will tie themselves in knots trying to strictly apply every guard rail it seems appropriate but in their desperation to provide a successful result will produce some of the weirdest and illogical solutions to problems that you've ever seen. Sometimes if there are too many guard rails agents will just miss them altogether! Other times, and this is perhaps the most sinister, agents will have no problem applying every guard rail that you throw at them but in doing so they purposely ignore better and/or more novel solutions to your problem that they could have easily had them implement for a better result but instead they remain quietly and maliciously compliant to the guard rails you've put in place and miss out on of the very things that can make developing with LLMs so brilliant!

So to ensure that Ang remains ever powerful, useful and accurate, I've actively take steps to try and keep the whole framework, simple, light weight and from an agent guidance perspective as light touch as possible. The hope is that this approach allows you to have a workflow that you as a human will be able to benefit from the repetition of, allowing you to keep track of the progress and flow of work through the framework as well as allowing you gain experience and skill driving simply through the repetition of using it instead of having to spend hours understanding the many varied nuances of the framework through hours of reading through documentation....or let's face it, through the **some** hours of reading an LLM generated summary of the documentation, lol. Equally, from an agent point of view keeping the tooling and guard rails light not only serves to protect each agent's context window but also allows the models that are running the workflow the freedom to provide you with the real value of not just being a quite little drone monotonously churning through tickets but a real tool for discoveries within your projects ecosystem which, sure, you might have arrived at yourself given the time and effort invested in deeper thinking and manual research on your own part but having these presented to you by your agents rather than having to discover them yourself manually is really the "juice" that makes working with LLMs to produce software worth the "squeeze" so that is the main driver and motivation behind us trying to keep the scope of tooling and guard rails that are implemented in Ang as lean as possible. This also helps keep Ang more easily manageable and maintainable at the same time as there are less guardrails and features to keep in check. In any case if there's one thing I think many of us have learned it's that if:  

> Make no mistakes

Wasn't going to be effective. Then:

> No seriously bro, don't make any mistakes of any kind

Is not going to be destined to be anymore effective anyway. So we might as well keep it simple!

#### Lean Reasoning

I've mentioned a few times throughout this document that LLMs can really aid in achieving the benefit of producing novel solutions to problems that you might not have thought of. Either because it required some lateral thing that you hadn't done yet or because it involved techniques or technologies that you weren't yet aware of or weren't experienced enough with yet. This is great, but it's only the first piece of the puzzle. Being made aware that there's a possible solution there doesn't instantly make it the correct choice! What needs to happen next is that you as the human need to gain the understanding needed to make the final decision as to whether the new proposed direction is actually the right choice in the context of your project and it's current state of implementation. This is something that, in my opinion, can not be left to LLM reasoning alone!

To address this Ang agents are instructed in a way that keeps their reasoning to accepting limits when they are helping you walk through the unknown. A concrete example of this is that when they are told to perform research tasks that they should not rely on reasoning alone to come to a conclusion. For me, I really don't care what the model was trained on if I'm trying to discover the truth about something new that I'm trying to learn, that's not how I would've learned before LLMs and I haven't seen anything from LLMs that would lead me to trust their ability to do this accurately now, at the end of the day this isn't what I want Ang agents to do for me when I set them on a research task. Before LLMs if I was instructing a less experienced colleague on how to perform a good research task on a topic like this my instruction would have been not to bring me a summary that was based entirely on their own knowledge and experience, there might be some value in that sure but, what I'd really be asking for is for them to collect information about the topic from sources who are already experts in this topic to try and understand the truth about the topic and how it applies to the software development process that we're trying to execute. And sure, there's room for the person performing the research to inject their own experiences to connect two pieces of evidence together in a way that tells us something new and/or interesting about how the topic might apply to our specific circumstances but this is entirely different to our "research" just being a list of the facts that the research already knew about the topic. This direction is exactly what I've implemented in Ang's research agents, and it manifests itself in the framework by having Ang's agents label information in what we've called Evidence Tiers so that future agents reading the research know how much weight to lay at the feet of any facts it's relying on to take actions during implementation. Listed from the most valuable and most important to be relied on when agents need to make decisions they are:

1. Evidence provided by the pilot of Ang. The next two first principles will delve deeper into this but ultimately the REAL human driving the software development process should always be considered the one who knows what is right, wrong or otherwise. They are the person who knows when to apply nuance and when, despite other tier's potentially disagreeing, a direction is the correct one to take during implementation, design or whatever else the evidence might be driving.
2. Evidence provided by sources from real authors. Ang agents are warned to be careful on relying on benchmarks sourced from the marketing websites of technologies we're researching, for example, but ultimately the opinion of what **real** experts sharing their **real** expertise is something that matters when it comes to trying to find the truth during research. Not withstanding that ET1 may suggest otherwise in some cases, ET2 provides direction that is worth taking into account when deciding what the output of a research task should be.
3. Evidence that has been reasoned. Just because models can be solely trusted to provide the results of research doesn't imply that they have ultimately been trained on ET2 sources. So although this tier will be frequently overruled by the tiers above, we can't deny that there is at least some value in the facts revealed by this tier.

The core of this section boils down to this: While reasoning is a valuable tool, it can never be as valuable as evidenced produced by **real** humans and Ang's agents should always acknowledge this fact.



### 2. You are the boss of Ang. Ang works for you, never the other way around.

The current climate of the software development industry is very confusing to me. It really seems like there are a couple of prevailing thoughts about the direction it's taking which taken independently are easy enough to accept but I find that each developer seems to hold multiple of them at the same time and when taken like this, to me at least, they kind of stop making sense. The statements I hear frequently when chatting to people about AI and it's place in software development as we move forward in the industry are:

- AI has taken the joy out of the job that used to get from coding, it feels like these days all I do is give directions to an AI chat bot who then goes and does the fun things I used to do.
- If you were hoping to continue your career as a "code-monkey" then you've got a hard road ahead of you. The job has changed, the future of being a software developer is no longer going to be involved with laboriously typing out code one line at a time. Software developers will now and forever be in charge of maintaining and directing LLMs to generate code, the skill is no longer in how well you remember syntax, it's in expressing your experience and wisdom through architecture, system design and product development. You're going to have to become ok with this or you will not survive in the industry!
- You should be every pushing towards the goal of achieving more and more automation within your software development workflows handing as much as possible off to LLMs so that you can avoid having to do things manually thus freeing your time to achieve even more productivity than would otherwise be possible. Some even go as far as to say that a "software factory" should be your ultimate end goal.

As I've said each of these things taken independently is perfectly valid. I personally do feel a great amount of revulsion at the idea that my job has become boiled down to essentially teaching a chat bot to solve my jigsaw puzzle for me, that sucks. But, the advent of LLM in software development workflows **most definitely** has meant that the age of "cave man" coding is over, there's just no reasonable excuse you could make to justify ignoring the benefits that an LLM brings to software development workflows. And finally, if we're going to have chat bots do all the work, it only makes sense that we use that extra time in our workday to get even more done! Automation has never been an easier tool to leverage and ignoring it doesn't serve anyone.

But it's when you start mixing and matching more than of these points that the whole thing starts to fall apart and I so frequently see people unironically doing so without batting an eye. Hand coding may have gone away, but it's true that the puzzle hasn't gone away completely it's just moved and there is definitely just as fulling puzzles to solve when it comes to system design and architecture. But let's not get ahead of ourselves, LLMs are just simply not ready (and possibly never will be) to be handed the keys to the castle entirely nor, in my opinion, even be handed them a little bit. This isn't a conversation I'm willing to enter in depth because it's not really the topic of this discussion but I honestly think that "software factories" are a psyop by frontier model companies to have us all boiling the ocean (literally!) with tokens desperately trying to make a swarm of models produce results by themselves while also having the output make any fucking sense what-so-ever! I'm of the opinion that to maintain any sort of consistency, accuracy and reliability, a human doesn't just need to be "in the loop" they need to be in control and steering the ship.

To me the only way to parse the three statements above in a way that makes any sense is as such:

- Our role has changed and coding has to take a back seat. It may suck, but it's a reality. However;
- That means that the way that we are now required to express and exercise our skill and expertise as developers is through being able to pilot LLMs to do that coding most effectively. Our value comes in being able to fill the gap that LLMs still have and possibly always will have in our ability to be able to make decisions, apply our wisdom and experience, apply nuance, use our creativity, and inject the hard requirements driven by the pressures and realities of the real world that we live in to help direct the flow of the software engineering process. These are the things that no matter how good LLMs get they are just not going to be able to replicate and it's the parts where software developers are still able to provide **real** value! Taking that to be true, then it's right to say;
- Automation in the software development process must have it's limits, and I believe those limits need to be set long before we start using terms like "human in the loop". The human needs to be driving the process. Sure that process can involving working with multiple agents at once to increase productivity but to me there's just no viable workflow that doesn't involve a human driving the process with their foot hovering over the brakes ready to slam them on at the first sign of an agent taking their own liberties and headed in a direction that threatens to waste vast amount of time and tokens hunting solutions for edge cases or use cases that literally no one asked for!

I could use more words to explain this but I think ultimately we've gotten to the core of it here. One of Ang's first principles is that the human should **always** be in charge of the software development process and should never be tempted to put themselves in a position where they'd be considered to be the ones in control of that process.

### 3. Ang is helpful. Ang is not simply a passive observer of the development process it's an active participant.

This principle exists more or less to avoid an over correction I had started to see in the early days of Ang's development which seemed to be a reaction to the previous principle. I had started to find that Ang's agents had become almost paralysed from making a decision almost fearful that taking any step by themselves would draw my ire. My bad I guess, haha!

This principle exists because while working with Ang agents in an area of the software development process that I am experience in (some maybe going as far as to call me an expert) it's imperative that I am at the centre of any and all decisions with regards to the direction of the project, there are many other areas of the development process where I am **not** an expert. When you consider what I've said in the previous section you'll note that it's vital that I am at the core of any decision making process because that is, at the end of the day, where I exert and express my experience, knowledge and wisdom to produce the ideal results that we're aiming for. But when we're working in areas where I have less experience or knowledge to express the shifts slightly. I should still be in control of the final end decision, necessarily because the results produced are going to be entering the world with my name on it and I'll be claiming it as "work I've done" and making guarantees to the people I deliver the work to as to it's quality and accuracy. But also before I can confidently make those decisions and later the assertions that I think they're correct I need to be brought up to speed on what the options are, what they mean, what the up and downsides to them are and how I can expect them to impact the specific work I'm doing. I'm trying to "pin the tail on the donkey" here and as per the previous section I'm most certainly not going to be handing this decision off to an LLM, this what this first principle exists to resolve.

Ang agents are instructed that when we're entering a field that is unknown to me the goal of the process shifts slightly. No longer are Ang's agents aiming to just defer every decision off to me. There's no value there because at this point I wouldn't trust myself to be able to make the right decision anymore than I would trust an LLM  to! The goal of Ang's agents in this position is to meet me where I am at, and then help guide me to the point where I've gained the knowledge needed to confidently make a decision. Sometimes this might be through executing research and providing me with sources that I can draw from to understand the problem we're trying to solve in a more holistic fashion. Other times this might be just to help me organise many, seemingly disconnected or opposing thoughts, into a plan that I can action so that I can have a starting point, see a goal and find a path between two like what you can see in the concept of "raw files" which I'll explain in more details later.

What this principle boils down to is that even thought I, as the pilot of Ang, should be the final arbiter of all decisions and considered the final and most accurate truth on any topic, this does not make me infallible and all knowing. And the goal of Ang's agents should be able to know when we've discovered a chink in my armour and at that point need to shift the way they operate to taking a more active role in the development process through helping guide me and giving me structure such that I can arrive confidently back in my intended role as the project's ultimate steer. This is much more desirable when compared to the agent's I had before this first principle was introduced who would defer any and all decisions to me regardless of the context and then happily stall the entire project waiting to "hear what the boss says" safe in the knowledge that they'd successful applied the previous principle!

### 4. Get your own bastard framework, Ang is mine!

This final first principle was born as I began entertaining the idea of releasing Ang as an open source framework. The drivers for it were:

1. As Ang becomes open source how can I ensure that the principles above are still adhered to?
2. How do I make it so that there's value in releasing Ang as an open source framework i.e. release it in a form that a wider open source community will actually find useful, while still keeping it in a state that is still useful and tailored to serving me?
3. How do I avoid becoming an open source maintainer?!

As I move Ang to becoming an open source project, if it gets any sort of traction then I won't be the only person with opinions for how it should be function. But I know from my experience building it and using it extensively that a great deal of the value that I'm able to derive from Ang is directly from having Ang agents adhering to these principles and ensuring that they are honoured when it comes to modifying/maintaining the framework. If, when Ang is open sourced, there are people with differing opinions on this I will be very unlikely to want to budge on this as I know it's at the heart of what makes Ang a great tool for me. Equally, if you look at this point at a more granular level if we ignore any of Ang's first principles then we risk walking the framework slowly towards the exact traps that the principles have been put in place to try and avoid! For instance if I suddenly start accepting a heap of PR's adding more and more additional features to Ang then there's a real risk that it evolves into just another over encumbered framework, and as XKCD pointed out many years ago, the last thing the software industry needs is another developer with good intentions inadvertently creating yet another competing standard that we all now suddenly have to follow!

Another point of friction for me finds it home in the very motivation I had for creating Ang in the first place. As I went through the trials and tribulations of repeating the cycle of introducing another AI-assisted framework to my workflow only to find it falling to pieces in my hands after a few months what really perplexed me was how the people presenting these frameworks were managing to hold them together and **really** drive their development processes. I refused to believe that all of them were purely making these so that they could present them in the next series of developer conference talks they had planned. Not only because not all of the frameworks seemed to have been authored by professional conference talk speakers but even if they were in order for them to speak about them so confidently they must have found some modicum of success at some point for them to have had the motivation to continue to build and improve them or else what would be the point. I had hoped that the common factor wasn't just me, but unfortunately the evidence was definitely pointing that way. After a while though I came to the conclusion that the problem was me, but not for the reason that you or I might have expected. I think that the reason why the authors of these frameworks see so much success with them is because they are ultimately built and tailored with the sole purpose and intention to perfectly serve exactly the way that they see success in their software development endeavours. The authors of the frameworks will likely never see the problems that I've seen in their frameworks because even though at a high level we are all trying to achieve the same goal in largely the same ways, when you consider what I've said in previous sections about how software development is now less about how we write code and more about how we are able to express our skill and talent through the medium of software development it's easy to see that software development has become less deterministic in it's nature. When we were measuring success through code there was syntax that was correct or it wasn't, tests that were green or red, etc. architecture and so forth played a big role in the success of a project but it shared a large part of the stage with code that is, for the most part, right or it's not. In this new age of software development the less deterministic parts of the endeavour takes the stage almost entirely alone and because of that being able to define a single "way of doing things" becomes far more difficult. Even though we are all reading from the same hymn sheet at a high level there is far more room for our development processes to be a unique snowflake, doing things in our own, very specific, slightly different ways and frameworks supporting this really have a colossal task before them if they're going to make attempts to codify that in the rigid structure of a framework!

Finally, let's be brutally honest here, I do lovely the nature of the free transfer of knowledge and communal nature of the software development industry. I've taken opportunities to be a part of it many times in my past but the realities of my life as it stands means that I simply do not have the time and effort to invest in becoming an open source maintainer. I have very little free time as it is and the little free time I do have simply can't be reserved for release processes, PR reviews and/or arguments in disgruntled issue threads. Love it or hate it, it's a reality, I simply can't find myself in a position where I'd be relied upon to maintain Ang if it sees any modicum of success.

As I spent time contemplating these issues I realised that all three of them could be somewhat solved by bringing into focus more sharply exactly what I thought Ang is, what it isn't, what Ang is trying to achieve, how it's trying to achieve it differently than frameworks that already exist and ultimately what value I thought that Ang stood to provide to an open source community. Hopefully by following this train of thought it might become clear to you too how the very nature of Ang solves all three of the problems listed above:

- Ang is a light-weight, light touch framework. While it has enough of a feature set to ensure that it is effective and valuable the second it's "taken out the box" it is never intended to be something that will solve every problem under every circumstance, because;
- Ang is malleable. If it doesn't do something that is vital to your own software development workflow then within a session or two you can have raised a workflow improvement and then had the Ang agents work to implement the change you want to see in the framework in no time at all, so;
- If Ang doesn't want to see your PR that tailors Ang towards supporting the way that **you** like to deliver software. If it doesn't do something you want it to do, you don't have to wait for the next release to enjoy the tailored experience you're wishing it had. The tools have been provided for you to quickly and easily enjoy those benefits so why are we bothering to introduce the friction of all this ceremony?! Because at the end of the day;
- Ang might be open source, but it's not owned by an open source community. It's yours, to do what you want with and make it perfectly fit the ways that you want it to work.

So you can see that by exploring this definition of what Ang is, all three of the problems above are solved. For the avoidance of doubt, let's run through them quickly. Ang's first principles will always be adhered to within the open sourced root repo because there's simply no need for them to change there. The open sourced root repo isn't Ang, it's the starter. You can find value in it's usage out the box but it's intention was never to be the finishing point, it was to give your boost you needed to build a software development framework that is your own. And in your own Ang instance you might decide that these first principle deserve to be changed or added to or deleted outright?! All of that is fine because your instance of Ang and the Ang open source repo are different things that serve different purposes. So it follows that my own instance of Ang is equally, not the open source repo, so I never have to worry about the needs of the open source repo and my own needs for how Ang needs to function to support my workflow colliding in a way that makes either less useful for the purposes they're trying to serve. So finally, I never have to worry about being inundated with PRs to the Ang repo because at the end of the day, if you're raising a PR against Ang then there's an overwhelming chance that you've missed the point of Ang entirely! I'm not perfect I make mistakes and there certainly may be ways that Ang the open sourced repo might be able to be modified to better achieve it's purposes but in all likelihood the correct response to the large majority of issues or PR's raised is "Cool idea, you should go build it!"

Don't use Claude and want Ang to work with Codex? Sure, I'm positive you will be able to have Codex agents help you with that. Have a specific part your workflow that you want codified in Ang, treat yo self, just raise a workflow improvement. Want a specific way that Ang likes to do things in it's native workflows, go for your life! At the end of the day Ang isn't the open source repo, it's your own instance that you've changed however you want to see it changed!

The real upshot of all this is that Ang should really be a framework that gets better and more useful to you through the process of you simply using it over time. As you progress working with Ang it should become more and more your framework of choice not because it's so comprehensive out the box but because over time as you use it the framework supports you in being able to tailor it until it perfectly fits you rather than you going on the impossible search to find a framework that fits you directly out the box.

## How I personally intend to use Ang

The benefits of Ang that I've listed above have been achieved through Ang's implementation in way that I expect for it to support my usage of it pretty much perfectly out of the box. In my day to day work there are a couple of different ways that I use Ang, the main ones are:

- To support the work I do through contracts for my clients; and
- To support the work I do on the software products that my business builds and sells

Both of these modes of development are well supported natively via Ang. For my contracting work this will involve dropping Ang in alongside the repos that I'm working in for my clients and Ang will be able to boostrap my claude harnesses and populate the initial Ang context via the bootstrap brownfield command. From there I'm all set up to start dropping notes I've taken during on boarding with the client and/or tickets I've been assigned into the raw folder and I'm off to the races working on the client's project work!

Then when I'm working through the process of coming up with a new idea for a product Ang will be there in my fresh repo waiting for my first long, rambling brain dump in the raw folder so it can start cutting it up and helping me organised my long unstructured throughs into discrete workstreams that I can start executing against!

If I find either of these process involve any friction or I need to create new and specific workflows to support the specific project I'm working on then I'll raise a workflow improvement and then I might find that I actually end up with a series of Ang instances all slightly different and all perfectly tailored to delivering the software project that I'm trying to deliver!

In this way you can see a worked example of Ang's intended usage and how it achieves what I've described in saying "Ang isn't and open sourced framework so much as it is a starter for creating workflows that perfectly fit and support the project that you're trying to deliver with Ang!"

## Some clarity - What exactly are "raw" files and how are they used

While performing the work that we do off the back of this raw file I do believe that a large majority of the context you're going to need can be derived from Ang's implementation files themselves I think it's worth taking the time to provide a little bit more context around the intention and usage of raw files within the framework. Here I'm specifically referring to files that go into the raw folder within the framework.

The raw folder came into existence within the framework driven originally by a need that I wanted to support that I couldn't find any other framework could support in the way I needed it to. Specifically, I had a great many ideas for a single new software product I wanted to build. I knew that there would be a **lot** of different things that would have to be considered across architecture, implementation, sales, marketing, etc. some of these areas I had firm ideas already on how I wanted them done, others I was less sure about and some I didn't any any idea of the first thing I needed to look into to get started! Then there were any number of thoughts in between! The problem I had is that I had this huge mess of thoughts, unstructured, unlinked and I had no idea how I was going to organise them in a way that would allow me the vision and clarity to be able to group them in together in logical units that could be worked on and moved forward in a way that made sense and walked me closer to my goals. If I had a process that could do this for me that would give me a great starting point to jump off from and take the reigns of the project from there. That's where the idea for raw files were born, the idea being that I would open a new markdown file and just start pouring my brain on to the page. Every thought I had, idea I wanted to explored and thing I was as yet under of just dump into a document. Then I wanted an agent to take that and organise it in a work streams that I could begin working on. And so I built Ang to provide with this functionality.

This is one thing that raw files provide an answer for but equally, not every project begins like this. As I've mentioned above there is regular business as usual work both on my products and the projects I work on for clients that have ever shifting requirements that needs to be supported. A surprise ticket assigned to me by a client's team, an random "shower thought" I had this morning about a product I'm working on, a news article that I read that changes the shape of the landscape a product I'm building lives in, a random slack or discord conversation I've just had with another developer. All these things stand to change the shape and direction of a project either by adding new work that needs to be done or possibly redirecting work that is already in progress and I felt that Ang needed to support this. And so it does, through raw files. The raw files don't simply need to take the shape of the brain dumps provided above, they can, indeed be anything that the agent's harness can ingest. During an ideate session the agent's task is to review and analyse the raw files and decide what they mean to the ongoing project and then make suggestions (and later action them) as to how things need to change with regards to the delivery in order to address these new concerns. A new ticket might get a separate work stream to be worked on and maybe it also now blocks the workstream of a ticket already in flight! A news article changing the landscape might be minor enough to demote an in flight work stream from execution back to planning for a bit of a rethink for before continuing or maybe it justifies it's own workstream dedicated solely to working out what exactly this new information means to the project.

The point here is that the raw files exist in the workflow to essentially take any unstructured input that Ang's pilot thinks might be relevant to the project that Ang is working on and help with the process of structuring the thoughts within and providing guidance on how that new information materially affects the project if at all and then providing a suggested pathway for how to begin moving forward in a way that acknowledges this changing delivery environment.

Within the repo you'll notice a couple of files that are in the unstaged set of changes, being `src/.claude/rules/working-with-zac.md` and `src/.claude/output-styles/partner-in-crime.md` these are files that currently exist in my working copy of Ang and the reason they aren't checked in is because they are very tailored towards me and how I like to see Ang working. - Have `/bootstrap-repo` offer a choice: take the defaults or customise them from the start.

## Where `ang.json` lives

A simple one here: `.claude/ang.json` is a symlink into `src/`, so this repo's config and the default that ships are the same file. We need to move it elsewhere, or have bootstrap create it.

## Streams off by default

Streams must not ship turned on. It is set to `"streams": false` for the initial check-in; make sure that stays the default whatever happens to `ang.json`.

## `/curate-tags` description

The description says "Use when … the tag count passes 50", but the skill has `disable-model-invocation: true`, so the model can never invoke it. In practice, `library validate` warns once the count passes 50 and the user runs the command.

- Suggested fix: keep the flag and reword the description: "Use when the user runs /curate-tags; library validate suggests it once the tag count passes 50."
- Keeping the flag matches the 15 other user-started skills and stops a sweeping rewrite landing in an unrelated session's diff.

## Ang is going to be open sourced

I've never actually attempted to **properly** release a repo I own as open source. I've worked in the open source community long enough to know that there are definitely accepted standards and things I like to see when I'm looking through open sourced project and I also know that the very nature of Ang means not every one of these standards are going to fit Ang perfectly and will either need to be modified or dropped. Also I don't want Ang to necessarily feel like it needs to suit the high standards set by repositories like React etc. I'm not a huge corporation and have no interest in pretending to be one! So I think it's going to be worth doing some research on open sourced projects particularly ones that aren't afraid to use a little whimsy interest me as that suits my style and persona very well, and see what they're doing and which parts of their process we could afford to lift.

I've already added the MIT license to Ang and I'm happy enough with that, I was considering WTFPL for a while but ended up deciding that there was no reason to be edgy just for the sake of it. I honestly don't think there's any real need for things liek PR or issue templates unless they're absolute no brainers to implement, even then we don't need to invest too much time in those. Same thing can be said for a CONTRIBUTORS.md. All of this is because as you've seen from the context in this document the entire core of what Ang is means that if we've done things right, these should never happen at a volume where investing time them really matters! You could say a similar thing about CI/CD I don't think there's any real value in linting markdown files although perhaps the code files could use it, I guess I'm on the fence about how much time we invest in ensuring that code quality in the repo is a first class citizen, I wouldn't say I'm completely against it but I'd need to convinced of it's value.

Really what this work stream represents in my head right now is that I need to discover what sort of things I might need to consider before pushing this project properly out as an open sourced project, then which of them I think suits Ang to implement, which of them I'd like to change to suit my style and which of them I think we really don't need and should be dropped, and from there we need to go about implementing these things.
